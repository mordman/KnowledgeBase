Склейка строк в цикле

Классика из код-ревью: log += item внутри цикла. Каждый += создаёт новую строку — на 200 итераций это 200 объектов и квадратичная работа копирования.

Before.cs200 аллокаций
string log = "";
foreach (var p in positions)      // 200 элементов
    log += p.Name + "; ";         // новая строка каждый раз
return log;
After.cs1 буфер
var sb = new StringBuilder(positions.Count * 8);
foreach (var p in positions)
    sb.Append(p.Name).Append("; "); // пишет в свой буфер
return sb.ToString();               // одна финальная строка

дуэль 2

LINQ-цепочка против цикла по Span

LINQ прекрасен для читаемости, но каждая операция — итератор + делегат. В горячем цикле на 10 000 элементов это заметно. Ручной цикл по Span к тому же векторизуется JIT-ом.

Before.cs6+ объектов
var total = positions
    .Where(p => p.Qty > 0)       // итератор + Func-делегат
    .Select(p => p.Qty * p.Price) // ещё итератор + делегат
    .Sum();                       // перечисление всей цепочки
After.cs0 аллокаций + SIMD
decimal total = 0;
foreach (var p in positions.AsSpan()) // struct-энумератор
    if (p.Qty > 0)
        total += p.Qty * p.Price;     // простой цикл → векторизация
Замер: 10 000 элементов
✗ LINQ-цепочка

время—
✓ foreach + Span
объектов на вызов0
время—
Нюанс: вне горячих путей выбирайте LINQ — читаемость дороже микровыгоды. Правило: оптимизируем только то, что показал профилировщик.

дуэль 3

Неявный boxing структур

Структуры в ArrayList / object-параметрах / интерфейсных вызовах молча упаковываются в кучу. Тысяча элементов — тысяча коробок по 24+ байта и работа для GC.

Before.cs1000 коробок
var box = new ArrayList();         // object[] внутри
foreach (var pt in points)         // struct Point
    box.Add(pt);                   // box ×1000!
int sum = 0;
foreach (object o in box)
    sum += ((Point)o).X;           // unbox каждый раз
After.cs0 коробок
var list = new List<Point>(points.Length); // generic
foreach (var pt in points)
    list.Add(pt);                  // структура лежит как есть
int sum = 0;
foreach (var pt in list)
    sum += pt.X;                   // никакого unbox

дуэль 4

Буфер на каждый запрос

Сервис обрабатывает 50 запросов, каждому нужен временный буфер 64 КБ. new byte[65536] каждый раз — это 3,2 МБ мусора, почти всё в LOH. ArrayPool арендует один буфер и гоняет его по кругу.

Before.cs50 × 64 КБ
void Handle(Request r)
{
    var buf = new byte[65_536];    // аллокация на каждый вызов
    Fill(buf);
    Send(buf);
}   // буфер станет мусором сразу после Send
After.cs1 буфер на всех
void Handle(Request r)
{
    var buf = ArrayPool<byte>.Shared.Rent(65_536);
    try { Fill(buf.AsSpan(0, 65_536)); Send(buf); }
    finally { ArrayPool<byte>.Shared.Return(buf); }
}
Замер: 50 запросов × 64 КБ
✗ new byte[]

Лямбда с захватом в цикле

Предикат, созданный внутри цикла и захвативший переменную, — это display-класс + делегат на каждой итерации. Вынесите лямбду в статическую и передайте состояние параметром — компилятор закэширует делегат один раз.

Before.cs2 объекта/итерация
foreach (var limit in limits)          // 1000 итераций
{
    var found = list.Find(x => x > limit); // захват limit:
    // каждый раз НОВЫЙ display-класс + делегат
}
After.csкэш на весь процесс
private static bool Greater((int X, int Lim) s)
    => s.X > s.Lim;                    // статическая, без захвата

foreach (var limit in limits)
    var found = list.Find(x => Greater((x, limit)));
// делегат один — в static-поле <>c.Cache

Квест: найдите 6 проблем в горячем методе

Этот метод вызывается тысячи раз в секунду. В нём 6 производительных проблем из изученных глав. Кликайте по подозрительным строкам: верная — объяснение, неверная — взбучка. найдено: 0/6

OrderService.cs — клик по строке = «здесь проблема»
ProcessOrder — hot path

Итог: отрефакторенный метод

After.csвсе 6 проблем устранены
private readonly StringBuilder _log = new(128);       // 1) переиспользуемый буфер

public async Task<string> ProcessOrderAsync(Order order)  // 6) async до конца
{
    _log.Clear();
    foreach (var p in order.Positions)
        _log.Append(p.Name).Append("; ");                  // 1) без +=

    List<int> qtys = new(order.Positions.Count);           // 2+3) generic, без boxing
    foreach (var p in order.Positions)
        qtys.Add(p.Qty);

    var buf = ArrayPool<byte>.Shared.Rent(65_536);         // 4) аренда вместо new
    try
    {
        Fill(buf.AsSpan(0, 65_536));
        decimal sum = 0;
        foreach (var p in order.Positions)                 // 5) простой цикл вместо LINQ
            if (p.Qty > order.Limit)
                sum += p.Qty * p.Price;
        await SendAsync(buf, sum);                         // 6) await вместо .Wait()
    }
    finally { ArrayPool<byte>.Shared.Return(buf); }
    return _log.ToString();
}

Зачёт практикума счёт: 0/5

1. С чего начинается любая оптимизация?

Оптимизация без замера — суеверие. К тому же профилировщик регулярно показывает, что узкое место совсем не там, где казалось.

2. Почему после замены LINQ на цикл нужно перезапустить бенчмарк, а не просто поверить глазам?

Рефакторинг без тестов и повторного замера — лотерея: можно и ускорить не то, и сломать семантику (например, отложенное выполнение LINQ).

3. Что не так с new byte[65_536] в обработчике каждого запроса?

Большие короткоживущие массивы — худший сценарий для кучи. Пул буферов устраняет и аллокации, и фрагментацию LOH.

4. task.Wait() внутри обработчика ASP.NET-запроса — почему это плохо?

Каждый заблокированный поток — минус рабочая единица пула. Async-ожидание паркует задачу, а поток забирает следующий запрос.

5. Лямбда x => x > limit внутри цикла — что аллоцируется на каждой итерации и как исправить?

Захват переменной превращает лямбду в метод экземпляра сгенерированного класса. Статическая лямбда без захвата кэшируется в <>c.Cache один раз на программу.
