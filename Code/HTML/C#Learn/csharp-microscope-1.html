01

компиляция и исполнение

Путь кода: C# → IL → машинный код

Компилятор C# не создаёт машинный код — он собирает сборку с IL (Intermediate Language) и метаданными. При первом вызове метода JIT-компилятор переводит IL в машинные инструкции. С .NET Core работает tiered compilation: горячие методы сначала компилируются быстро (Tier-0), а когда метод «разогрелся» — перекомпилируются с оптимизациями (Tier-1). Вызовите метод и посмотрите:

int Add(int a, int b) => a + b;

Tiered compilation: Tier-0 компилируется быстро и без оптимизаций (чтобы приложение стартовало быстрее), на горячих методах (~порог вызовов) включается Tier-1: инлайнинг, PGO (оптимизация по профилю), удаление проверок границ. Есть также NativeAOT — компиляция в машинный код заранее, без JIT, ценой гибкости.
02

память

Анатомия объекта: 16 байт, которых вы не писали

Каждый объект в куче начинается с заголовка: sync block (нужен для lock, хэш-кода, номера поколения GC) и указатель на MethodTable — «паспорт типа» с vtable виртуальных методов. Поэтому самый маленький класс занимает минимум 24 байта на x64, даже с пустым телом. Структуры заголовка не имеют — в этом их дешевизна. Выберите тип и кликните по сегментам:

04

сборка мусора

GC: поколения, mark и compact

Сборщик делит кучу на поколения: гипотеза «большинство объектов умирает молодыми». Новые объекты попадают в gen 0; пережившие сборку продвигаются в gen 1, затем в gen 2. Маленькие сборки частые и дешёвые, gen 2 — редкие и дорогие. Объекты > 85 КБ идут сразу в LOH и не уплотняются. Кликайте по объектам, чтобы сделать их «укоренёнными» (живыми), и запускайте сборку:

GEN 1 — пережившие одну сборку
GEN 2 — долгожители (полная сборка)
LOH — объекты > 85 000 байт (не уплотняется)
аллоцировано: 0 освобождено: 0 сборок: g0 0 · g1 0 · g2 0 последняя пауза: —
клик по объекту = корень (стек/статика/регистры): сборщик его не тронет; тусклые — мусор

Жизненный цикл: allocate — почти бесплатно (просто сдвиг указателя в gen 0); collect(0) — часто, миллисекунды; пережившие сборку едут в gen 1/2. Поэтому лучшая оптимизация под GC — меньше аллоцировать: переиспользовать буферы, пулы объектов (ArrayPool<T>), структуры вместо классов в hot-путях.

цена финализации

Финализаторы: объект умирает дважды

Объект с финализатором (~Class()) CLR регистрирует в специальной очереди. На первой сборке такой объект нельзя освобождать: он продлевает себе жизнь и попадает в f-reachable, пока отдельный поток финализаторов (один на процесс!) не выполнит финализатор. И только на следующей сборке объект умрёт. Сравните судьбы двух объектов:

Два объекта, две судьбы
using var a = new Res()
создан · Dispose() вызван
var b = new Res() — забыт
создан · зарегистрирован в очереди финализации
f-reachable queue: пусто
Resource.csправильный паттерн
class Res : IDisposable
{
    ~Res() { /* финализатор: аварийная уборка */ }

    public void Dispose()
    {
        Cleanup();                     // освободить сейчас
        GC.SuppressFinalize(this);     // вычеркнуть из очереди!
    }
}

using var a = new Res();  // Dispose вызовется сам в конце блока
Выводы: финализатор удлиняет жизнь объекта минимум на две сборки и нагружает единственный поток финализаторов. Dispose + using — детерминированно и дёшево; финализатор — только страховка для unmanaged-ресурсов. В .NET вместо финализаторов чаще берут SafeHandle.

полиморфизм внутри

MethodTable и разрешение виртуальных вызовов

У каждого типа есть MethodTable со слотами виртуальных методов. Инструкция callvirt берёт MethodTable фактического объекта и прыгает в нужный слот — так работает полиморфизм. Невиртуальные и sealed-вызовы JIT заменяет прямым call (devirtualization) — без таблицы. Проследите путь вызова:

Разрешение вызова
METHOD TABLE + VTABLE
slot 0Speak → …
slot 1Walk → Animal.Walk
Dispatch.cscallvirt vs call
class Animal
{
    public virtual string Speak() => "…";  // попадает в vtable
    public void Walk() { }                 // обычный call
}
class Dog : Animal
{
    public override string Speak() => "Гав!"; // тот же слот!
}
sealed class SealedCat : Animal
{
    public override string Speak() => "Мяу!";
}

Animal a = new Dog();
a.Speak();  // IL: callvirt → MethodTable(Dog) → slot 0
// sealed/невиртуальный вызов JIT часто превращает
// в прямой call — одна инструкция, без таблицы.
Интерфейсные вызовы дороже виртуальных: у каждого типа своя карта интерфейсов, слот ищется через неё. Поэтому в горячих циклах List<T> c for бывает заметно быстрее foreach через IEnumerable<T>.

лямбды внутри

Замыкания: display-классы и ловушка цикла

Когда лямбда захватывает переменную, компилятор создаёт display-класс в куче: переменная становится его полем, а делегат хранит ссылку на экземпляр. Лямбда без захвата — статический кэш <>c<>.Instance, ноль аллокаций. Классическая ловушка: переменная цикла for у всех лямбд одна.

Что создаст компилятор?
Ловушка переменной цикла
foreach начиная с C# 5 создаёт новую переменную на каждой итерации — там ловушки нет. В for переменная одна на весь цикл: лямбды захватывают её, а не снимок значения. Лечение: локальная копия внутри тела цикла.

машина генератора

yield return: итератор — это state machine

Метод с yield return компилируется в класс-итератор с полем состояния: тело не выполняется при вызове — оно возобновляется по одному шагу на каждый MoveNext(), запоминая, где остановилось. Пошагайте вручную:

IEnumerable<int> Squares()
state: ещё не создан Current: —
IEnumerable<int> Squares()
{
for (int i = 1; i <= 3; i++)
yield return i * i; // пауза
}
выдано:
Iterator.csчто генерирует компилятор
// Грубый эквивалент сгенерированного класса:
class Squares_Enumerator : IEnumerator<int>
{
    int state = 0, i, current;
    public bool MoveNext()
    {
        // state 0: вход, i = 1
        // state 1: проверить i <= 3, current = i*i,
        //          state = 2, return true  (пауза!)
        // state 2: i++, goto state 1
        // конец: return false
    }
    public int Current => current;
}
// Следствия: один аллоцированный объект-итератор,
// отложенное выполнение, повторный foreach = новый итератор.

асинхронность внутри

async/await: машина состояний под капотом

Каждый async-метод компилируется в структуру, реализующую IAsyncStateMachine: поле state, локальные переменные как поля, метод MoveNext(). На незавершённом await метод возвращает управление, регистрируя продолжение; поток освобождается. Пройдите по шагам:

LoadAsync() — пошагово
state: — поток: занят поля автомата: a=?, b=?
async Task<string> LoadAsync()
{
var a = await GetA(); // state 0 → 1
var b = await GetB(a); // state 1 → 2
return a + b;
}
StateMachine.csцена и оптимизации
// Эквивалент того, что строит компилятор:
struct LoadAsync_SM : IAsyncStateMachine
{
    public int state;          // -1 выполняется, 0,1,2…
    public string a, b;        // локальные переменные
    TaskAwaiter<string> aw;
    public void MoveNext() { /* switch (state) … */ }
}

// Оптимизации .NET 6+:
// 1) await уже завершённой задачи — без «парковки», синхронно
// 2) пул объектов состояния — меньше аллокаций
// 3) ValueTask / IValueTaskSource — для очень частых вызовов
// 4) AsyncMethodBuilder-кастомизация для библиотек
Продолжение возвращается туда, откуда ждали: в UI-потоке — через SynchronizationContext, в библиотеках без контекста — в пул. Отсюда правило: в библиотеках ConfigureAwait(false), и никакого .Result поверх async — классический дедлок строится именно на этом механизме.

Два прохода: поиск обработчика и раскрутка

Когда брошено исключение, CLR делает два прохода по стеку вызовов: первый ищет подходящий catch, второй — раскручивает стек, выполняя finally в пройденных кадрах. Исключение — объект, и stack trace заполняется в момент throw. Запустите:

Стек вызовов: Main → A → B → C
Main — точка входа
A() — catch (DivideByZeroException)
B() — только finally
C() — здесь бросят исключение

Экзамен Счёт: 0/10

1. Сколько байт занимает пустой class Empty { } на x64?

Заголовок обязателен у любого объекта в куче: sync block для lock/хэш-кода и указатель на MethodTable. Минимум 24 байта на x64 (16 на x86).
Q2.cs
int i = 42;
object o = i;

2. Где теперь живёт значение 42 из переменной o?

Это boxing: аллокация ~24 байта в куче и копирование значения. Каждая новая упаковка — новый объект.

3. Когда запускается сборка gen 0?

Сборка триггерится давлением аллокаций: бюджет gen 0 исчерпан → сборка, выжившие продвигаются в gen 1. Поэтому дешевле всего — меньше аллоцировать.

4. Объект с финализатором забыли задиспозить. Минимум сколько сборок GC нужно до освобождения памяти?

Объект переживает первую сборку (его нельзя трогать до финализации), поток финализаторов вызывает ~Class(), и только следующая сборка освобождает память. Плюс объект успевает попасть в старшее поколение.
Q5.cs
string a = "мир";
string b = "мир";
Console.WriteLine(ReferenceEquals(a, b));

5. Что выведется?

Компилятор заносит литералы в пул интернированных строк: одинаковый текст — одна ссылка на всё приложение. Конкатенация переменных создаёт новые объекты вне пула.

6. Animal a = new Dog(); a.Speak(); — по чему CLR находит реализацию Speak?

callvirt берёт указатель MethodTable из заголовка объекта — а там тип Dog. Так и работает полиморфизм: слот один, реализации разные.

var acts = new List<Action>();

    acts.Add(() => Console.Write(i));

7. Что напечатается?

Все лямбды захватили одну переменную i из display-класса. К моменту вызова цикл завершён и i == 3. Спасает локальная копия: int local = i внутри цикла. В foreach (с C# 5) переменная новая на каждой итерации.

8. Метод с yield return вызван, но результат ещё никто не перебирал. Что уже выполнилось из тела?

Вызов возвращает объект-итератор, тело стартует только при перечислении и приостанавливается на каждом yield return. Поэтому бросить исключение проверки аргументов до foreach не получится (частый источник багов).

9. В async-методе стоит await уже завершённой задачи (например, кэш вернул результат сразу). Что сделает машина состояний?

awaiter.IsCompleted == true → продолжаем сразу. На этом строятся fast-path кэшей и ValueTask: частый синхронный результат без аллокаций и переключений.

10. Почему Span<T> запрещено хранить в полях класса или захватывать в лямбду?

ref struct — гарантия компилятора: указатель/срез никогда не окажется в куче и не «повиснет» после освобождения памяти. Это безопасность нулевой цены без сборщика.
