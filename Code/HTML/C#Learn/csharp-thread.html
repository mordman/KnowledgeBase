01

теория · фундамент

Процесс → поток → задача

Процесс — изолированный контейнер запущенной программы: своё адресное пространство, свои дескрипторы. Поток — единица исполнения внутри процесса: у него свой стек (~1 МБ), свои регистры, но общая куча с остальными потоками. Именно потоки ОС распределяет по ядрам CPU и переключает между собой.

Task — это не поток. Это «обещание результата»: абстракция над работой, которую выполнит пул потоков, таймер или порт завершения I/O. async-метод возвращает Task и может вообще не занимать поток на время ожидания.

Зачем это нужно

① Параллелизм — загрузить все ядра CPU-задачей. ② Отзывчивость — не замораживать UI, пока идёт долгая работа. ③ Асинхронный I/O — сеть и диск через IOCP-порты завершения: пока ждём ответ сервера, ни один поток не занят.

пример 1 · от простого

Свои потоки: порядок не гарантирован

Два потока выполняют одну и ту же функцию. Кто и когда получит процессорное время — решает планировщик ОС и CLR. Запустите симуляцию несколько раз: порядок строк каждый раз разный. Вывод: никогда не стройте логику на предположении «этот поток выполнится первым».

Симуляция переключений
Program.cs
using System.Threading;

void Work(string name)
{
    for (int i = 0; i < 4; i++)
        Console.WriteLine($"{name}: шаг {i}");
}

var t1 = new Thread(() => Work("Поток-1"));
var t2 = new Thread(() => Work("Поток-2"));
t1.Start();
t2.Start();
t1.Join();  // дождаться завершения (если нужно)

// Порядок строк в консоли случаен
// и меняется от запуска к запуску
Thread сегодня нужен редко: фоновые long-running задачи с приоритетом, COM/STA-модели. Для 99% случаев берите Task.Run и пул потоков — он переиспользует потоки и балансирует очередь work-stealing алгоритмом.

пример 2 · параллельность

Завтрак: 23 минуты или 8?

Классический пример из документации Microsoft: яичница (8 мин), бекон (6), кофе (3), тост (4), сок (2). Готовить по очереди — 23 минуты. Запустить всё одновременно и дождаться через Task.WhenAll — 8 минут (длительность самой долгой задачи). Нажмите оба режима и посмотрите на диаграмму Ганта.

Кухня: диаграмма Ганта
Breakfast.cs23 минуты
// Каждая операция блокирует до готовности
void MakeBreakfast()
{
    CookEggs();    // ждём 8 мин
    CookBacon();   // ещё 6 мин
    MakeCoffee();  // ещё 3 мин
    MakeToast();   // ещё 4 мин
    PourJuice();   // ещё 2 мин
}
BreakfastAsync.cs8 минут
// Запустили всё сразу, ждём один раз
async Task MakeBreakfastAsync()
{
    Task eggs   = CookEggsAsync();
    Task bacon  = CookBaconAsync();
    Task coffee = MakeCoffeeAsync();
    Task toast  = MakeToastAsync();
    Task juice  = PourJuiceAsync();

    await Task.WhenAll(eggs, bacon, coffee, toast, juice);
}
// Есть и Task.WhenAny — «кто закончил первым»
Важно: параллельность здесь возможна, потому что задачи независимы и в основном ждут внешние устройства (плиту, тостер). Если бы они делили одну сковороду — понадобилась бы синхронизация. К ней вернёмся в разделе 05.

пример 3 · механика

async/await изнутри

await не создаёт поток и не блокирует его. Компилятор разрезает метод на конечный автомат: локальные переменные уезжают в объект состояния, поток освобождается, а продолжение (continuation) возвращается, когда задача завершится — в UI-поток через SynchronizationContext или в пул. Кликните по шагам:

await ≠ поток. await Task.Delay(5000) — это таймер, потоки не заняты. Thread.Sleep(5000) — поток стоит и ничего не делает. Разницу почувствуете ниже.
StateMachine.csшаг 1/4
async Task<string> LoadAsync()
{
    var url = BuildUrl();                       // выполняется сразу
    var data = await Http.GetStringAsync(url);  // паркуемся здесь
    return Parse(data);                         // продолжение
}

Почему это важно для UI: блокировка против await

Два одинаковых окна. В обоих — кнопка-счётчик и кнопка «Загрузить данные на 1,6 секунды». Левое окно блокирует свой поток (Thread.Sleep), правое — использует await Task.Delay. Попробуйте кликать по счётчикам во время загрузки.

MainWindow — Thread.Sleep (ПЛОХО)
окно отвечает
MainWindow — await Task.Delay (ХОРОШО)
окно отвечает
Левое окно подвисло по-настоящему — страница реально не обрабатывала клики 1,6 секунды, потому что JS (как и UI-поток WPF) один, и его заняли. Именно так выглядит .Result, .Wait() или Thread.Sleep в обработчике кнопки.
Bad.csблокирует UI
// ПЛОХО: UI-поток занят всё время загрузки
void OnLoad(object s, EventArgs e)
{
    Thread.Sleep(1600);      // или .Result / .Wait()
    var data = Download();
    Show(data);              // окно «не отвечает»
}
Good.csUI жив
// ХОРОШО: поток свободен, продолжение
// вернётся в UI-поток через SynchronizationContext
async void OnLoad(object s, EventArgs e)
{
    var data = await DownloadAsync();
    Show(data);
}

Гонки, lock и дедлоки

counter++ — это три операции: прочитать, прибавить, записать. Если два потока выполняют их вперемешку, чужая запись перекрывает нашу — инкремент теряется. Это состояние гонки (race condition). Запустите симуляцию без блокировки несколько раз — итог почти никогда не равен ожидаемому. Затем включите lock.

Дедлок: два потока, два ресурса

Для дедлока нужны 4 условия: взаимное исключение, «держи и жди», отсутствие вытеснения и циклическое ожидание. Ломаем любое — дедлок исчезает. Проще всего — порядок захвата ресурсов: все потоки берут их одинаково.

Mutex — единственный «межпроцессный» примитив

В отличие от lock/Monitor, именованный Mutex виден другим процессам ОС — это способ договориться между разными программами (или копиями одной). Классика — защита от второго экземпляра приложения.

Особенности: захватить и освободить должен один и тот же поток (thread affinity); если поток умер, не отпустив мьютекс, следующий владелец получит AbandonedMutexException — сигнал, что где-то упал процесс. Медленнее Monitor: это объект ядра ОС.

SingleInstance.csмежду процессами
// Имя с префиксом Global\ видно всем сессиям ОС
using var mutex = new Mutex(false, @"Global\MyApp.Single");

if (!mutex.WaitOne(0))
{
    Console.WriteLine("Приложение уже запущено");
    return;
}

try
{
    // … работаем в единственном экземпляре …
}
finally
{
    mutex.ReleaseMutex(); // тот же поток, что захватил!
}

Channel<T>: производитель и потребитель

Производитель быстрее потребителя — буфер растёт. Ограничим его тремя элементами: когда буфер полон, WriteAsync ждёт — это backpressure, система сама притормаживает быстрых. Наблюдайте за статусом производителя.

    await foreach (var item in ch.Reader.ReadAllAsync())

практика · проверка себя

Квиз: что выведет код?

Семь вопросов с подвохом — ровно те грабли, на которые наступают все. Счёт: 0/7

Q1.cs
for (int i = 0; i < 5; i++)
    new Thread(() => Console.Write(i)).Start();

Что может появиться в консоли?

Лямбда захватывает переменную i, а не её значение. К моменту старта потоков цикл может давно завершиться и i станет равен 5. Лечение: int local = i; внутри цикла и захват local.
Q2.cs
Console.Write("A");
Thread.Sleep(1000);   // в асинхронном контексте
Console.Write("B");
// против
await Task.Delay(1000);

Чем Thread.Sleep отличается от await Task.Delay?

Thread.Sleep замораживает поток (в UI — всё окно). Task.Delay — таймер: поток возвращается пулу и выполняет другую работу, а продолжение приходит по сигналу.
Q3.cs
async Task<int> GetAsync()
{
    Console.Write("A");
    await Task.Delay(1000);
    Console.Write("B");
    return 42;
}

GetAsync();
Console.Write("C");

Что выведется?

async-метод выполняется синхронно только до первого незавершённого await, затем возвращает управление вызывающему. Поэтому «C» печатается сразу, а «B» — через секунду, когда придёт продолжение.
Q4.cs
// Вызывается из UI-потока WPF/WinForms
public string GetName()
{
    var task = httpClient.GetStringAsync(url);
    return task.Result;   // ???
}

Что не так с этим кодом?

Это «sync-over-async». Продолжение задачи хочет вернуться в UI-поток, а UI-поток заблокирован ожиданием .Result — классический дедлок (особенно в WPF/WinForms/старом ASP.NET). Решение: сделать метод async и написать await.
Q5.cs
public void Save(Order o)
{
    lock (this)      // «защищаем состояние объекта»
    {
        db.Write(o);
    }
}

Почему lock(this) — плохая практика?

Монитор вешается на публично доступный объект. Правильно: приватное поле private readonly object _sync = new(); и lock по нему. По тем же причинам не лочат typeof(T) и строки (интернирование).
Q6.cs
var list = new List<int>();
Parallel.For(0, 1000, i => list.Add(i));
Console.WriteLine(list.Count);

Что произойдёт?

Обычные коллекции (List, Dictionary) не рассчитаны на конкурентную запись. Варианты: обернуть Add в lock, взять ConcurrentQueue/ConcurrentDictionary или собрать результаты через возвращаемые значения.
Q7.cs
await Task.Delay(5000);

Что await делает с текущим потоком на время ожидания?

В этом суть async: на ожидании I/O потоки не простаивают. Метод «помнит» себя в объекте конечного автомата, а когда задача завершится, продолжение возобновляет его с того же места — с теми же локальными переменными.

  • пробрасывайте CancellationToken и проверяйте его в долгих циклах
  • освобождайте блокировки в finally / using
  • держите критические секции короткими: вошёл → сделал → вышел

✗ Не делайте

  • async void вне обработчиков событий — исключения улетят «в никуда»
  • .Result / .Wait() поверх async — sync-over-async: голодание пула и дедлоки
  • lock(this), lock(typeof(T)), lock("строка")
  • await внутри lock — это ошибка компиляции; нужен SemaphoreSlim(1,1)
  • new Thread(…) на каждый запрос — для этого есть пул
  • не полагайтесь на порядок выполнения потоков
