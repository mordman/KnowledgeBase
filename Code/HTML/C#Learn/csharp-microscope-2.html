планирование

ThreadPool и work-stealing изнутри

У пула потоков одна глобальная очередь (под замком) и по локальному двустороннему deque на каждый поток. Свой поток берёт задачи с головы своего deque (LIFO — дружит с кэшем); когда deque пуст — крадёт с хвоста чужого. Если все потоки заняты блокирующим ожиданием, CLR медленно добавляет новые (hill climbing, ~500 мс на шаг) — поэтому блокировки в пуле так болезненны. Наблюдайте за кражами:

Главный урок: поток пула, заблокированный на .Wait(), lock или синхронном HTTP-вызове, не выполняет ничего, а замена ему приходит через сотни миллисекунд. Это и есть причина «всё тормозит под нагрузкой» в sync-over-async коде. Лечение: async I/O, либо выделенные потоки для блокирующей работы.

много ядер

Модель памяти: почему другие ядра видят старое

У каждого ядра свой кэш, а CPU и компилятор имеют право переставлять операции чтения/записи, если поток однопоточен. Поэтому запись data = 42; flag = true; может стать видимой другому ядру в обратном порядке: флаг уже true, а данные ещё 0. Барьеры (fence) запрещают такие переносы. Прогоните серию испытаний:

T1: data=42; flag=true  ·  T2: if (flag) print(data)
Ядро 0 — поток T1 (пишет)
кэш: data —
кэш: flag —
память: data 0 · flag false
Ядро 1 — поток T2 (читает)
читает flag false
читает data 0
Visibility.csклассический баг
int data = 0;  bool flag = false;

// T1:                          // T2:
data = 42;                      if (flag)               // увидели true
flag = true;                        Console.WriteLine(data);
// без барьера T2 может вывести 0:
// CPU переставил записи / кэш ядра ещё не синхронизирован

// Инструменты барьеров:
volatile bool flag;      // барьеры вокруг чтения/записи
Interlocked.Increment(ref x);  // полный fence
lock (sync) { }          // барьеры на входе и выходе
Thread.MemoryBarrier();  // явный fence
Тонкость: volatile гарантирует видимость и запрещает переносы вокруг доступа, но не делает операции атомарными — volatile int n; n++ всё равно гонка. Атомарность дают Interlocked/lock, видимость — барьеры, и в x86-мире она «почти бесплатная», а на ARM — заметно строже.

SIMD: одна инструкция — восемь чисел

SIMD (Single Instruction, Multiple Data) обрабатывает вектор из нескольких чисел за один такт: Vector128 — 4 int, Vector256 — 8 int (AVX2), Vector512 — 16 (AVX-512). Сложение двух массивов на 8 элементов скалярно — 8 операций, вектором — одна. Сравните:

result[i] = a[i] + b[i] для 8 элементов

Пулы буферов: ArrayPool и ObjectPool

Каждый new byte[100_000] — это аллокация в куче и будущая работа GC; такие объекты идут в LOH и не уплотняются. Если буфер нужен на миллисекунды — берите его в аренду у ArrayPool<T>.Shared и возвращайте обратно: аллокация происходит один раз. Прогоните 20 «запросов» в двух режимах:

Правило выбора: буфер живёт дольше метода → ArrayPool; меньше 1 КБ и метод короткий → stackalloc; переиспользуемый сложный объект → ObjectPool. И всегда измеряйте: пул без нужды — лишняя сложность.

проверка

Экзамен второй части

Счёт: 0/8

1. Все потоки пула заняты блокирующим ожиданием, а задачи продолжают поступать. Что сделает CLR?

Hill climbing вводит потоки постепенно, чтобы не пересоздать их сотни. Отсюда латентность при резкой нагрузке и польза SetMinThreads для latency-сценариев — и главная причина не блокировать потоки пула.

2. Work-stealing: как поток берёт задачи из локального deque и как крадёт у других?

LIFO у себя = свежие задачи в кэше; кража с противоположного конца снижает конкуренцию с владельцем. Глобальная очередь нужна только для «чужих» задач.

3. Что гарантирует volatile bool flag?

volatile — про барьеры и видимость. flag = true увидят все, но n++ над volatile-полем всё равно гонка: чтение-изменение-запись не атомарны.

4. Какая операция включает полный барьер памяти (full fence)?

Операции Interlocked — это атомарность + полный барьер. Барьеры также ставят lock (на входе/выходе), volatile-доступы (половинные) и явный Thread.MemoryBarrier().

5. Vector256<float> на машине с AVX2 обрабатывает за одну инструкцию…

256 бит / 32 бита на float = 8 дорожек. Vector128 — 4 float, Vector512 — 16. Реальная выгода упирается в скорость памяти, поэтому SIMD особенно хорош, когда данные уже в кэше.

6. Вы вызвали ArrayPool<byte>.Shared.Rent(1000). Что важно помнить?

Пул округляет размеры до бакетов (16, 32, 64… элементов), поэтому Rent может вернуть больший массив. Очистка — только опцией clearArray: true. Забытый Return = утечка из пула и новая аллокация в следующий раз.

7. Почему аренда буфера из пула снижает нагрузку на GC?

Сборка стартует, когда исчерпан бюджет поколения. Меньше аллокаций — реже сборка, меньше копирований при компакции, LOH не засоряется большими короткоживущими массивами.

8. В высоконагруженном сервисе долгие синхронные блокировки в обработчиках. Симптом — латентность растёт, CPU при этом не загружен. Diagnosis?

Классический почерк голодания пула: очередь растёт, потоки заблокированы, CPU простаивает, а подмена потоков медленная. Лечится асинхронным I/O, SetMinThreads и устранением блокировок в hot-path.
