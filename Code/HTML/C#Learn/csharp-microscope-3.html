асинхронность глубже

ValueTask: когда Task слишком тяжёлый

Task — класс: каждый незавершённый вызов аллоцирует объект в куче. Если метод в 90% случаев возвращает результат синхронно (кэш, буфер, быстрая проверка), это чистый мусор. ValueTask<T> — структура: синхронный путь не аллоцирует ничего, а для редкого асинхронного пути .NET 6+ использует пул объектов через IValueTaskSource. Прогоните 100 вызовов «кэша» в обоих режимах:

GetUserAsync(id) — 90% попаданий в кэш

Cache.csсинхронный fast-path
private readonly Dictionary<int, User> _cache = new();

public ValueTask<User> GetUserAsync(int id)
{
    if (_cache.TryGetValue(id, out var u))
        return new ValueTask<User>(u);   // 0 аллокаций!
    return LoadSlowAsync(id);            // редкий путь
}

private async ValueTask<User> LoadSlowAsync(int id)
{
    var raw = await _http.GetStringAsync($"/u/{id}");
    return _cache[id] = Parse(raw);
}

producer / consumer

Channel<T>: что внутри между писателем и читателем

Канал — это буфер + две очереди ожидающих. Когда буфер полон, WriteAsync ставит продюсера в очередь ожидания (backpressure — система сама тормозит быстрых); когда пуст — ReadAsync паркует консьюмера. Никто никого не блокирует: ожидание асинхронное. Попробуйте обе стороны руками:

Channel.CreateBounded<int>(3)
продюсер: WriteAsync свободен
консьюмер: ReadAsync свободен
записано: 0
прочитано: 0
дрейф буфера: 0
Pipeline.csполный цикл
var ch = Channel.CreateBounded<Job>(new BoundedChannelOptions(3)
{
    FullMode = BoundedChannelFullMode.Wait,   // backpressure
    SingleReader = true, SingleWriter = false
});

async Task ProduceAsync()
{
    await foreach (var job in IncomingJobs())
        await ch.Writer.WriteAsync(job);  // полон? ждём
    ch.Writer.Complete();                 // «больше не будет»
}

await foreach (var job in ch.Reader.ReadAllAsync())
    Process(job);   // канал закрыт и пуст → цикл завершится сам
VsBlockingCollection.csне блокируем потоки
// BlockingCollection<T> — эпоха потоков:
foreach (var x in bc.GetConsumingEnumerable())
// поток СТОИТ в ожидании — минус поток пула

// Channel<T> — эпоха async:
await foreach (var x in ch.Reader.ReadAllAsync())
// ожидание — это await, потоки свободны

// Бонусы Channel: TryWrite/TryRead без ожидания,
// WaitToReadAsync/WaitToWriteAsync, Completion-таск,
// UnboundedChannelOptions, DropOldest/DropWrite
// как альтернатива Wait для «некритичных» данных.
Где применять: фоновые очереди в ASP.NET (вместо «пожарных» Task.Run), конвейеры обработки стримов, развязка быстрых продюсеров и медленных консьюмеров. Бонус: bounded-канал — готовый ограничитель нагрузки без семафоров.

низкий уровень

unsafe: указатели и арифметика адресов

В unsafe-коде C# превращается в почти C: настоящие указатели, ручные адреса, нулевая безопасность. Ключевой момент — fixed: GC умеет двигать объекты при уплотнении кучи, поэтому перед взятием указателя объект нужно закрепить. int* p + 1 сдвигает адрес не на 1, а на sizeof(int) = 4 байта. Походите по памяти:

int arr[6] в куче
p не инициализирован — нажмите fixed
Pointers.cs/unsafe
unsafe void Sum(int[] arr)
{
    fixed (int* p = arr)          // закрепить: GC не тронет
    {
        int* end = p + arr.Length;
        for (int* q = p; q < end; q++)   // +1 = +4 байта
            *q *= 2;                     // пишем прямо в память
    }                               // unpin: GC снова свободен
}

// Маршалинг и совместимость:
fixed (byte* b = bytes)
    NativeLib.Process(b, bytes.Length);
// stackalloc + указатели:
int* buf = stackalloc int[16];
Modern.csа нужен ли unsafe?
// Сегодня 95% задач unsafe решаются безопасно:

Span<int> s = arr;              // вместо fixed + int*
ref int first = ref s[0];       // вместо *p
MemoryMarshal.GetArrayDataReference(arr); // без fixed

// unsafe остаётся для: P/Invoke со старыми API,
// ручного парсинга бинарных форматов на пределе
// производительности, работы с нативной памятью
// (NativeMemory.Alloc) и совместимости с C/C++.
Цена unsafe: отключение проверок верифицируемости сборки, ответственность за каждую ошибку памяти на вас (привет, segfault-подобные падения и порча кучи), и никакой помощи GC. Правило: Span и ref — по умолчанию, unsafe — когда измерили и доказали необходимость.

компиляция

JIT против NativeAOT: кто когда платит

JIT-модель платит за компиляцию при запуске и по ходу работы — зато знает реальный профиль нагрузки (tiering, PGO). NativeAOT компилирует всё в машинный код до запуска (ILC): старт почти мгновенный, бинарник самодостаточный, но без рантайм-генерации кода, а рефлексия требует явных подсказок для trimming. Сравните запуски:

dotnet run (JIT)
загрузка сборки, метаданных +25 мс
JIT первых методов (Tier-0) +40 мс
работа приложения…
горячие методы: фоновая перекомпиляция Tier-1 +15 мс
время до первой строки вывода: 0 мс
app (NativeAOT)
загрузка нативного образа +8 мс
сразу выполнение Main
никакой компиляции в рантайме
время до первой строки вывода: 0 мс

Когда что выбирать: NativeAOT — serverless/контейнеры/CLI, где критичны холодный старт и размер образа. Классический JIT — большие сервера с долгим аптаймом, где tiering/PGO дают выигрыш, и где активно используется рефлексия и динамическая загрузка. Есть и средний путь: ReadyToRun/PGO-профили для JIT-сборок.

Экзамен третьей части

Счёт: 0/8

1. Главное ограничение ValueTask по сравнению с Task?

ValueTask — структура-обёртка, которая после await «разряжается» (особенно при пулированном IValueTaskSource). Повторное ожидание или AsTask несколько раз — undefined behavior. Нужно несколько потребителей — сначала ConvertToTask/AsTask один раз.

2. Когда ValueTask действительно выгоднее Task?

Выгода — в отсутствии аллокации на синхронном завершении. Если метод почти всегда реально асинхронный, обычный Task проще и безопаснее: цена аллокации тонет в стоимости I/O.

3. Чем Channel<T> принципиально отличается от BlockingCollection<T>?

ReadAllAsync/WriteAsync паркуют ожидание как задачу, освобождая потоки пула. BlockingCollection.GetConsumingEnumerable держит поток в блокировке — в асинхронном мире это лишний занятый поток.

4. Зачем нужен fixed перед взятием указателя на массив?

Без закрепления первая же сборка может переместить массив, и указатель станет указывать в чужую память. fixed держит объект на месте до конца блока, потом unpin.

5. int* p указывает на arr[0]. Что делает p + 1?

Арифметика указателей масштабируется типом: p+1 для int* = +4 байта, для double* = +8. Именно поэтому p[i] эквивалентно *(p+i). Для увеличения значения нужно (*p)++.

6. Главное архитектурное следствие NativeAOT?

ILC компилирует заранее и вырезает неиспользуемый код (trimming). Поэтому Assembly.Emit, часть рефлексии и некоторые сериализаторы требуют явных подсказок [DynamicallyAccessedMembers]. Плюсы: мгновенный старт, маленький образ, отсутствие рантайма.

7. В JIT-приложении метод стал горячим. Что произойдёт?

Tiered compilation: сначала быстрый Tier-0 ради старта, затем фоновая перекомпиляция горячих методов с профилем реального исполнения. Приложение при этом не останавливается — просто меняется адрес кода.

8. Продакшен-сервис стал тормозить. Какой счётчик первым подскажет, что пул потоков голодает?

Растущая очередь пула при свободном CPU — классический почерк starvation: потоки стоят в блокировках, а hill climbing подкладывает новые с задержкой. Лечим async I/O и устранением блокировок.
