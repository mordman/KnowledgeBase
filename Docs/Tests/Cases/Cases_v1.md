### 1.1 Функциональное тестирование (Functional Testing)
**Объект:** Корзина интернет-магазина электроники.

---

#### Тест-кейс FUNC-01: Добавление товара, которого нет в наличии (Out of Stock)

| Поле | Значение |
|------|----------|
| **ID** | FUNC-CART-01 |
| **Приоритет** | Высокий (High) |
| **Тип** | Функциональное |

**Предусловия:**
1. Пользователь авторизован в системе.
2. В базе данных для товара «Смартфон X» установлено количество на складе = 0.
3. Флаг «Скрыть отсутствующие товары» в настройках магазина отключен.

**Шаги:**
1. Открыть карточку товара «Смартфон X».
2. Обратить внимание на статус кнопки «Купить/В корзину».
3. Попытаться добавить товар через прямой API-запрос `POST /api/cart/add` (обход UI).

**Ожидаемый результат:**
- На UI кнопка «В корзину» неактивна (disabled) и заменена на текст «Нет в наличии» или «Сообщить о поступлении».
- При попытке добавления через API сервер возвращает `HTTP 400 Bad Request` с кодом ошибки `OUT_OF_STOCK`. В корзину товар не добавляется.

---

#### Тест-кейс FUNC-02: Применение промокода на бесплатную доставку

| Поле | Значение |
|------|----------|
| **ID** | FUNC-CART-02 |
| **Приоритет** | Средний (Medium) |
| **Тип** | Функциональное |

**Предусловия:**
1. В корзине находится товар на сумму 4500 руб.
2. Минимальная сумма для бесплатной доставки по промокоду `FREEDEL` — 5000 руб.

**Шаги:**
1. Перейти в раздел «Корзина».
2. Ввести промокод `FREEDEL` в соответствующее поле.
3. Нажать кнопку «Применить».
4. Добавить в корзину ещё один товар стоимостью 1000 руб. (итоговая сумма станет 5500 руб.).

**Ожидаемый результат:**
- На шаге 3 появляется уведомление: *"До бесплатной доставки не хватает 500 руб."*. Стоимость доставки остаётся стандартной (300 руб.).
- На шаге 4 стоимость доставки автоматически становится 0 руб., появляется бейдж *"Промокод применен"*. Итоговая сумма заказа корректно пересчитывается.

### 1.3 Нагрузочное тестирование (Performance / Load Testing)
**Объект:** API эндпоинт поиска `/api/v1/search?q={query}`.

---

#### Тест-кейс PERF-01: Стресс-тестирование — поиск точки отказа

| Поле | Значение |
|------|----------|
| **ID** | PERF-API-01 |
| **Приоритет** | Высокий (High) |
| **Тип** | Нагрузочное (Stress) |

**Предусловия:** Тестовый стенд развёрнут. БД заполнена 10 млн товаров. Инструмент: JMeter / k6.

**Шаги:**
1. Настроить линейный рост нагрузки: от 100 до 10 000 RPS за 15 минут.
2. Запустить тест.
3. Проанализировать графики Response Time и Error Rate.

**Ожидаемый результат:**
- До 3000 RPS p95 времени отклика < 200 мс.
- При 5000 RPS сервер не падает с `HTTP 500`, а отдаёт `HTTP 429 Too Many Requests` (Rate Limiter).

---

#### Тест-кейс PERF-02: Тестирование стабильности (Soak / Endurance)

| Поле | Значение |
|------|----------|
| **ID** | PERF-API-02 |
| **Приоритет** | Средний (Medium) |
| **Тип** | Нагрузочное (Soak) |

**Предусловия:** Стабильная нагрузка 80% от пиковой (2500 RPS).

**Шаги:**
1. Запустить подачу нагрузки на 24 часа.
2. Мониторить RAM, CPU, GC, Connection Pool.

**Ожидаемый результат:**
- Утечки памяти отсутствуют. График RAM стабилен.
- Время отклика не деградирует к концу теста. p95 < 250 мс.

---

#### Тест-кейс PERF-03: Spike Testing (резкий скачок трафика)

| Поле | Значение |
|------|----------|
| **ID** | PERF-API-03 |
| **Приоритет** | Средний (Medium) |
| **Тип** | Нагрузочное (Spike) |

**Предусловия:** Эмуляция старта распродажи.

**Шаги:**
1. Поддерживать фоновую нагрузку 200 RPS (5 мин).
2. Мгновенно увеличить до 8000 RPS за 10 секунд.
3. Удерживать 5 минут.
4. Резко сбросить до 200 RPS.

**Ожидаемый результат:**
- Во время скачка допускается увеличение RT до 1–2 секунд, но не потеря коннекта с БД.
- После снижения нагрузки система масштабируется вниз, RT возвращается к <150 мс за 2 минуты.

### 2.1 Конкурентное тестирование (Concurrency / Race Condition)

#### Тест-кейс BANK-CONC-01: Защита от Double Spend при параллельных списаниях

| Поле | Значение |
|------|----------|
| **ID** | BANK-CONC-01 |
| **Приоритет** | Критический (Critical) |
| **Тип** | Конкурентное / Безопасность |

**Предусловия:**
1. Баланс счёта клиента А = 1000 руб.
2. Настроено два параллельных потока.

**Шаги:**
1. Инициировать перевод 1000 руб. на счёт Б (Thread 1).
2. *Одновременно* инициировать перевод 1000 руб. на счёт В (Thread 2).
3. Проверить состояние счёта А в БД и логи транзакций.

**Ожидаемый результат:**
- Срабатывает Row-level locking.
- Только ОДИН запрос получает `SUCCESS` (баланс = 0).
- Второй запрос: `HTTP 400 / 402 Insufficient Funds`.
- Баланс никогда не уходит в минус (если овердрафт не разрешён).

### 2.2 Функциональное тестирование (Идемпотентность)

| Поле | Значение |
|------|----------|
| **ID** | BANK-FUNC-02 |
| **Приоритет** | Высокий (High) |
| **Тип** | Функциональное / Интеграционное |

**Предусловия:** Клиент оплачивает ЖКХ. Шлюз генерирует `Idempotency-Key` (UUID).

**Шаги:**

**Ожидаемый результат:**
- Сервер распознаёт ключ, НЕ списывает повторно.
- Возвращает `HTTP 200 OK` с оригинальным ID транзакции.
- В выписке — только одно списание.

### 2.5 Тестирование отказоустойчивости (Failover)

#### Тест-кейс BANK-FAIL-05: Падение Primary БД во время массового эквайринга

| Поле | Значение |
|------|----------|
| **ID** | BANK-FAIL-05 |
| **Приоритет** | Критический (Critical) |
| **Тип** | Отказоустойчивость |

**Предусловия:**
1. Нагрузочный генератор: 5000 TPS на авторизацию карт.
2. Кластер БД (Primary-Replica) с автофейловером (Patroni / PostgreSQL).

**Шаги:**
1. Запустить нагрузку.
2. `kill -9` на Primary-ноде БД.

- Во время переключения: `HTTP 503` или очередь. Двойных списаний нет.
- Транзакции в `processing` не теряются. После восстановления — завершение или reversal.

### Ключевые выводы и рекомендации

1. **Банк** — домен, где на первом месте стоят **идемпотентность**, **целостность транзакций** и **защита от Race Conditions**. Любая потеря или дублирование транзакции ведёт к прямым финансовым потерям и регуляторным штрафам.

2. **Биржа** — домен **сверхнизких задержек** и **математической точности**. Здесь критичны порядок исполнения (FIFO), защита от проскальзывания и строгая сверка в конце дня. Допустимое отклонение — 0.

3. **Аптека** — домен **комплаенса и безопасности пациента**. Критичны: контроль сроков годности (FEFO), рецептурный учёт, маркировка (МДЛП), холодовая цепь, лимиты на прекурсоры. Ошибка здесь может стоить здоровья.

4. **Общее правило:** для каждого домена необходимо покрывать не только "позитивные" сценарии, но и:
   - Граничные условия (пороговые значения, нулевые балансы)
   - Аварийные сценарии (падение сети, отказ ДЦ, тайм-ауты)
   - Злоумышленные действия (инъекции, подмена подписи, обход лимитов)
   - Конкурентный доступ (параллельные транзакции, одновременные брони)
