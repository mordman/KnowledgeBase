# Назначение `TestID`, `RequirementID`, `LinkedIssue`

Три поля образуют **цепочку трассируемости** в нашем наборе из 100 кейсов:

```
RequirementID  →  LinkedIssue  →  TestID  →  AutomationScript  →  BugID
(что нужно)       (как делаем)    (чем проверяем)  (чем автоматизируем)  (что нашли)
```

Пример сквозной цепочки для биржевого домена:
```
BRQ-PORT-006  →  STORY-2604  →  TC-PORT-004  →  tests/e2e/test_risk.py::test_stop_out  →  BUG-4521
(стоп-аут<5с)     (реализация)    (кейс)           (автотест)                              (найденный баг)
```

Ниже — разбор каждого поля по одной структуре: что это, зачем, где используется, отличие, практика, что было бы без него, итог.

---

# ЧАСТЬ 1. `RequirementID` — «что должно работать»

## 1.1. Что это

Уникальный идентификатор **бизнес-требования**. В нашем наборе — `BRQ-<Домен>-<Номер>`: `BRQ-ORDER-001`, `BRQ-PORT-006`, `BRQ-SEC-001`, `BRQ-NFR-001`.

Формат:
- `BRQ` — Business ReQuirement,
- `<Домен>` — `ORDER`, `PORT`, `STOCK`, `BOND`, `FUT`, `API`, `SEC`, `NFR`, `UI`, `UX`, `L10N`, `COMP`, `REG`,
- `<Номер>` — порядковый номер.

## 1.2. Назначение

### 1.2.1. Трассируемость «требование ↔ тест»
Показывает, **какое именно требование проверяет каждый кейс** и наоборот. Без него матрица трассируемости — просто список тестов.

**Пример:**
- `BRQ-PORT-006` — «Стоп-аут срабатывает <5 сек»,
- покрывающий кейс — `TC-PORT-004`.
- Требование меняется (SLA 5→3 сек) → точно знаете, что обновить `TC-PORT-004`, а не искать по всему набору.

### 1.2.2. Метрика покрытия требований
```
Requirement Coverage = (BRQ с ≥1 тестом) / (всего BRQ) × 100%
```
Позволяет увидеть пробелы: появилось `BRQ-FUT-011` без тестов — сразу видно.

### 1.2.3. Обратная трассируемость
При падении теста или баге за один шаг видно: требование → историю → владельца → спринт.

### 1.2.4. Регуляторика
ЦБ, SEC, FCA требуют **доказательства покрытия** критичных функций. Матрица «требование → тест → результат» — аудиторский артефакт. Без `RequirementID` вы не докажете, что требование «аудит всех операций» проверено (`BRQ-ORDER-010` → `TC-ORDER-010`).

### 1.2.5. Impact analysis при изменении
Требование `BRQ-BOND-002` (расчёт НКД) поменялось → через `RequirementID` находим все связанные тесты (`TC-BOND-002`, `TC-BOND-001`, `TC-PORT-008`) за секунды, вместо перезапуска всего регресса.

## 1.3. Где используется

| Место | Как |
|---|---|
| **CSV** | колонка `RequirementID` |
| **JSON (TestRail)** | `custom_requirement_id` + в `refs` |
| **Матрица трассируемости** | левая часть связи |
| **Jira/Xray/Zephyr** | связь Test ↔ Requirement, отчёт Test Coverage by Requirement |
| **CI/CD** | `pytest -m "requirement:BRQ-SEC-001"` — release gate |
| **SQL-аудит** | поиск требований без тестов |
| **Регуляторный отчёт** | приложение к аудиту |

## 1.4. Практика

**Поиск тестов по требованию (TestRail):**
```
refs:BRQ-SEC-001 → TC-SEC-001 (IDOR к портфелю)
```

**Поиск пробелов:**
```sql
SELECT r.id FROM requirements r
LEFT JOIN test_cases tc ON tc.requirement_id = r.id
WHERE tc.id IS NULL;  -- BRQ без покрытия
```

**Release gate:**
```bash
pytest -m "requirement:BRQ-PORT-006 or requirement:BRQ-SEC-001"
# падение любого → блок релиза
```

## 1.5. Что было бы без `RequirementID`

- Нет доказательства покрытия регулятору.
- Нет обратной трассируемости — при падении непонятно, какой функционал задет.
- Нет impact analysis — при изменении перезапускают весь регресс (дорого/долго).
- Нет метрики покрытия — неизвестно, что не протестировано.
- Нет release gate — релизят с падающими критичными тестами.
- Нет коммуникации с PO — «что-то тестировали» вместо «BRQ-X покрыт на 100%».

## 1.6. Итог

> **`RequirementID` — мост между бизнес-требованием и тестом; без него нет трассируемости, метрики покрытия, impact analysis, release gate и доказательств для регулятора.**

# ЧАСТЬ 2. `LinkedIssue` — «как реализуем»

## 2.1. Что это

Идентификатор **задачи реализации** в трекере (Jira, YouTrack). В нашем наборе — `STORY-<Номер>`: `STORY-1201`, `STORY-2604`, `STORY-1701`.

Формат:
- `STORY` — тип задачи (Story/Task/Bug/Epic),
- `<Номер>` — ID из трекера.

## 2.2. Назначение

### 2.2.1. Связь «бизнес ↔ разработка»
`RequirementID` отвечает на вопрос «что», `LinkedIssue` — на вопрос «кто и когда это делает».

**Схема:**
```
BRQ-PORT-006 (требование, owner = PO)
   ├── STORY-2604 (backend: стоп-аут)          — Dev A
   ├── STORY-2605 (UI: уведомление)            — Dev B
   └── STORY-2606 (интеграция с биржей)        — Dev C
         └── TC-PORT-004, TC-PORT-005, TC-REG-005
```

Одно требование → несколько историй → несколько тестов. Без `LinkedIssue` вы не видите, **какая реализация** покрыта тестом.

### 2.2.2. Прогресс спринта
По `LinkedIssue` видно, в каком спринте, кем и на каком этапе сделана реализация. Если `STORY-2604` ещё в `In Progress`, а тест `TC-PORT-004` уже `Passed` — сигнал, что тест проверяет мок, а не реальную реализацию.

### 2.2.3. Баг-трекинг и root cause
При баге цепочка `BugID → TestID → LinkedIssue` показывает, **в какой истории** закрался дефект.

**Пример:**
```
BUG-4521 → TC-PORT-004 → STORY-2604 (backend стоп-аута)
→ виновник: реализация в STORY-2604, а не в UI STORY-2605
```

### 2.2.4. Отчётность для менеджмента
- «Сколько историй спринта покрыто тестами?»
- «Какие истории без тестов?» — риск релиза.
- «Какие истории дали больше всего багов?» — качество реализации.

### 2.2.5. Связь с CI
При мердже PR, привязанного к `STORY-2604`, CI автоматически прогоняет тесты с `LinkedIssue=STORY-2604` — **точечная проверка изменений**.

## 2.3. Где используется

| Место | Как |
|---|---|
| **CSV** | колонка `LinkedIssue` |
| **JSON (TestRail)** | `custom_linked_issue` + в `refs` |
| **Матрица трассируемости** | правая часть связи |
| **Jira/Xray/Zephyr** | Test ↔ Story link, отчёт «Test Coverage by Story» |
| **CI/CD** | `pytest -m "story:STORY-2604"` — прогон по PR |
| **Баг-трекер** | цепочка Bug → Test → Story для root cause |

## 2.4. Практика

**Прогон по PR:**
```bash
# в PR указано: implements STORY-2604
pytest -m "story:STORY-2604"
```

**Поиск историй без тестов:**
```sql
SELECT s.id FROM stories s
LEFT JOIN test_cases tc ON tc.linked_issue = s.id
WHERE tc.id IS NULL;
```

**Root cause по багу:**
```
BUG-4521 → refs:TC-PORT-004 → LinkedIssue:STORY-2604
```

## 2.5. Что было бы без `LinkedIssue`

- Непонятно, **какая реализация** покрыта тестом (мок? старая версия? новая?).
- Нет связи «спринт ↔ тесты» — нельзя ответить «покрыт ли спринт».
- CI не может точечно прогонять тесты по PR.
- Root cause анализа нет: баг есть, а в какой истории — неизвестно.
- Нет отчёта «истории без тестов» — риск выпустить непротестированное.

## 2.6. Итог

> **`LinkedIssue` — мост между требованием и реализацией; без него тест живёт в вакууме и непонятно, что именно он проверяет и в каком спринте это сделано.**

# ЧАСТЬ 3. `TestID` — «чем проверяем»

## 3.1. Что это

Уникальный идентификатор **тест-кейса** в системе тест-менеджмента. В нашем наборе — `TC-<Домен>-<Номер>`: `TC-FUNC-001`, `TC-SEC-001`, `TC-PORT-004`.

Формат:
- `TC` — Test Case,
- `<Домен>` — `FUNC`, `UI`, `API`, `NEG`, `PERF`, `SEC`, `COMP`, `REG`, `USB`, `L10N`, `STOCK`, `BOND`, `FUT`, `ORDER`, `PORT`,
- `<Номер>` — порядковый номер.

## 3.2. Назначение

### 3.2.1. Однозначная идентификация
Позволяет ссылаться на тест из любого места: баг-трекера, CI-логов, отчётов, документации, коммуникации.

**Пример:**
> «Упал `TC-PORT-004` (стоп-аут)» — все понимают, о каком именно кейсе речь. Без ID было бы «тест на стоп-аут», а их 3–5 (API, UI, integration, regression).

### 3.2.2. Связь с багами (`BugID`)
При падении создаётся дефект с указанием `TestID` — источника обнаружения.

**Цепочка:**
```
TC-PORT-004 (упал) → BUG-4521 (создан) → STORY-2604 (фикс) → TC-PORT-004 (Passed)
```

В Jira-баге поле `Detected by test = TC-PORT-004` даёт:
- **воспроизводимость** — разработчик знает, каким тестом воспроизвести,
- **историю** — при повторном падении видно, что баг регрессировал,
- **метрику** — сколько багов найдено каждым тестом (test effectiveness).

### 3.2.3. Связь с автоматизацией (`AutomationScript`)
`TestID` → `AutomationScript` — прямая привязка ручного кейса к автотесту.

**Пример:**
```
TC-PORT-004 → tests/e2e/test_risk.py::test_stop_out
```

Позволяет:
- видеть, что автоматизировано, а что — ручное (`AutomationStatus`),
- при падении автотеста в CI сразу понять, **какой бизнес-сценарий** задет.

### 3.2.4. Стабильность и переиспользование
`TestID` не меняется при редактировании шагов/ожиданий. Это позволяет:
- вести историю прогонов (тренд Passed/Failed по кейсу),
- переиспользовать кейс в разных наборах (smoke, regression, release),
- считать flaky-тесты (кейсы с нестабильным статусом).

### 3.2.5. Наборы и фильтры
`TestID` — основа для наборов по платформам:
```
Mobile: TC-UI-001, TC-UI-003, TC-COMP-002, ...
Web:    TC-FUNC-001..005, TC-UI-001..005, ...
API:    TC-API-001..005, TC-SEC-001, TC-PERF-001..005, ...
```

## 3.3. Где используется

| Место | Как |
|---|---|
| **CSV** | колонка `ID` (первая) |
| **JSON (TestRail)** | `title` + `id` (после создания) |
| **Step-by-step CSV** | `ID` для склейки шагов |
| **Матрица трассируемости** | `TestID` — левая колонка |
| **Jira-баг** | `Detected by test` |
| **CI-логи** | `pytest` node id / TestRail case id |
| **Наборы платформ** | списки ID |
| **Метрики** | pass rate, flaky rate, test effectiveness по кейсу |

## 3.4. Практика

**Прогон конкретного кейса:**
```bash
pytest tests/e2e/test_risk.py::test_stop_out -v
```

**Поиск кейса по багу:**
```
BUG-4521 → Detected by test: TC-PORT-004 → tests/e2e/test_risk.py::test_stop_out
```

**Метрика test effectiveness:**
```sql
SELECT test_id, COUNT(bug_id) AS bugs_found
FROM test_runs tr JOIN bugs b ON b.test_id = tr.test_id
GROUP BY test_id ORDER BY bugs_found DESC;
```

**Flaky-кейсы:**
```sql
SELECT test_id, COUNT(*) FILTER (WHERE status='Failed') AS fails,
       COUNT(*) AS total
FROM test_runs WHERE run_date > now() - interval '30 days'
GROUP BY test_id HAVING fails > 0 AND fails < total;  -- нестабильные
```

## 3.5. Что было бы без `TestID`

- Нельзя однозначно сослаться на кейс — путаница «тест на стоп-аут» vs конкретный.
- Нет связи «баг ↔ тест» — непонятно, чем воспроизводить.
- Нет связи «кейс ↔ автотест» — ручные и авто живут отдельно.
- Нет истории прогонов по кейсу — нельзя отследить тренд, flaky, регрессии.
- Нельзя собрать наборы (smoke/regression/platform) — нет стабильного ключа.
- Нет метрик (pass rate, effectiveness, flaky) — нечем управлять качеством.

## 3.6. Итог

> **`TestID` — стабильный адрес тест-кейса; без него нет ссылок из багов, CI, отчётов, нет истории прогонов, метрик и наборов.**

# ЧАСТЬ 4. Три поля вместе — как они работают

## 4.1. Цепочка трассируемости

```
RequirementID  →  LinkedIssue  →  TestID  →  AutomationScript  →  BugID
     BRQ-*          STORY-*        TC-*        tests/...           BUG-*
     (что)          (как)          (чем)       (авто)              (что нашли)
```

**Сквозной пример (биржа):**
| Поле | Значение | Смысл |
|---|---|---|
| `RequirementID` | `BRQ-PORT-006` | «Стоп-аут <5 сек» |
| `LinkedIssue` | `STORY-2604` | Реализация backend стоп-аута |
| `TestID` | `TC-PORT-004` | Кейс «Стоп-аут» |
| `AutomationScript` | `tests/e2e/test_risk.py::test_stop_out` | Автотест |
| `BugID` | `BUG-4521` | Найденный дефект (SLA 8 сек вместо 5) |

## 4.2. Отчёты, которые строятся только на трёх полях

| Отчёт | Формула | Что даёт |
|---|---|---|
| **Requirement Coverage** | `BRQ с тестами / все BRQ` | Покрытие требований |
| **Story Coverage** | `STORY с тестами / все STORY` | Покрытие спринта |
| **Traceability Matrix** | `BRQ ↔ STORY ↔ TC` | Аудит, регуляторика |
| **Test Effectiveness** | `bugs / TC` | Какие тесты находят баги |
| **Flaky Rate** | `failed&passed / TC` | Нестабильные тесты |
| **Release Gate** | `critical BRQ → TC → status` | Блок релиза |
| **Impact Analysis** | `BRQ → все TC` | Что перезапустить |

## 4.3. Практические сценарии

### Сценарий 1. Пришёл баг от прода
```
BUG-5001 → Detected by test: TC-PORT-004 → LinkedIssue: STORY-2604
→ ответственный Dev A, спринт SP-19, требование BRQ-PORT-006
→ фикс в STORY-2604, перепрогон TC-PORT-004
```

### Сценарий 2. Изменилось требование
```
PM: «SLA стоп-аута 5→3 сек»
→ refs:BRQ-PORT-006 → TC-PORT-004, TC-PORT-005, TC-REG-005
→ перезапуск только этих + regression по STORY-2604
```

### Сценарий 3. Release gate
```bash
pytest -m "requirement:BRQ-PORT-006 or requirement:BRQ-SEC-001"
# падение → блок релиза, в логе: TC-PORT-004 Failed, STORY-2604, BRQ-PORT-006
```

### Сценарий 4. Аудит регулятора
```sql
SELECT tc.id, tc.status, tc.last_run, tc.requirement_id, tc.linked_issue
FROM test_cases tc
WHERE tc.requirement_id IN ('BRQ-ORDER-010','BRQ-PORT-010','BRQ-SEC-001')
  AND tc.status = 'Passed';
→ приложение к отчёту: «покрытие критичных требований 100%»
```

### Сценарий 5. Планирование спринта
```
SM: «Какие истории SP-19 без тестов?»
SELECT s.id FROM stories s
LEFT JOIN test_cases tc ON tc.linked_issue = s.id
WHERE s.sprint = 'SP-19' AND tc.id IS NULL;
→ список STORY без покрытия → добавить кейсы до релиза
```

## 4.4. Сравнительная таблица полей

| Поле | Отвечает на вопрос | Владелец | Пример | Меняется? |
|---|---|---|---|---|
| **`RequirementID`** | **Что** должно работать? | PO / BA | `BRQ-PORT-006` | При изменении бизнес-требования |
| **`LinkedIssue`** | **Как** реализуем? | Dev / SM | `STORY-2604` | При декомпозиции/переносе в спринт |
| **`TestID`** | **Чем** проверяем? | QA | `TC-PORT-004` | **Никогда** (стабильный адрес) |

Ключевое отличие: `RequirementID` и `LinkedIssue` — **бизнес-сущности** (меняются по воле бизнеса), `TestID` — **технический адрес** (стабилен на весь жизненный цикл кейса).

## 4.5. Что было бы без всех трёх

| Потеря | Последствие |
|---|---|
| Нет `RequirementID` | Нельзя доказать покрытие, нет impact analysis, нет release gate |
| Нет `LinkedIssue` | Непонятно, какая реализация покрыта, нет связи со спринтом |
| Нет `TestID` | Нельзя сослаться на кейс, нет истории прогонов, нет метрик |
| **Нет всех трёх** | **Набор тестов = плоский список без бизнес-смысла, без аудита, без управления качеством** |

## 4.6. Итог одной фразой

> **`RequirementID` + `LinkedIssue` + `TestID` — это вертикаль трассируемости «требование → реализация → проверка»; убрав любое звено, вы теряете либо доказательство покрытия, либо связь с разработкой, либо управляемость тестов.**
