### 1. Функциональное тестирование (Functional Testing)
**Объект:** Корзина интернет-магазина электроники.

#### Тест-кейс FUNC-01: Добавление товара, которого нет в наличии (Out of Stock)
*   **Приоритет:** Высокий (High)
*   **Предусловия:** 
    1. Пользователь авторизован в системе.
    2. В базе данных для товара «Смартфон X» установлено количество на складе = 0.
    3. Флаг «Скрыть отсутствующие товары» в настройках магазина отключен.
*   **Шаги:**
    1. Открыть карточку товара «Смартфон X».
    2. Обратить внимание на статус кнопки «Купить/В корзину».
    3. Попытаться добавить товар через прямое API-запрос `POST /api/cart/add` (обход UI).
*   **Ожидаемый результат:**
    *   На UI кнопка «В корзину» неактивна (disabled) и заменена на текст «Нет в наличии» или «Сообщить о поступлении».
    *   При попытке добавления через API сервер возвращает HTTP 400 Bad Request с кодом ошибки `OUT_OF_STOCK` и сообщением "Товар отсутствует на складе". В корзину товар не добавляется.

#### Тест-кейс FUNC-02: Применение промокода на бесплатную доставку
*   **Приоритет:** Средний (Medium)
*   **Предусловия:** 
    1. В корзине находится товар на сумму 4500 руб.
    2. Минимальная сумма для бесплатной доставки по промокоду `FREEDEL` — 5000 руб.
*   **Шаги:**
    1. Перейти в раздел «Корзина».
    2. Ввести промокод `FREEDEL` в соответствующее поле.
    3. Нажать кнопку «Применить».
    4. Добавить в корзину еще один товар стоимостью 1000 руб. (общая сумма станет 5500 руб.).
*   **Ожидаемый результат:**
    *   На шаге 3 появляется уведомление: "До бесплатной доставки не хватает 500 руб.". Стоимость доставки пересчитывается и остается стандартной (например, 300 руб.).
    *   На шаге 4 стоимость доставки автоматически становится 0 руб., появляется бейдж "Промокод применен". Итоговая сумма заказа корректно пересчитывается.

#### Тест-кейс FUNC-03: Очистка корзины при истечении сессии гостя
*   **Приоритет:** Низкий (Low)
*   **Предусловия:** Пользователь не авторизован (гость). В браузере отключено сохранение LocalStorage (или используется режим Инкогнито).
*   **Шаги:**
    1. Добавить два любых товара в корзину.
    2. Закрыть вкладку браузера.
    3. Открыть сайт заново через 24 часа (время жизни сессии гостя по ТЗ).
    4. Перейти в корзину.
*   **Ожидаемый результат:** Корзина пуста. Отображается сообщение "Ваша корзина была очищена".

### 2. Тестирование безопасности (Security Testing)
**Объект:** Форма аутентификации (Login) и профиль пользователя.

#### Тест-кейс SEC-01: Защита от SQL-инъекции (SQLi) в поле логина
*   **Приоритет:** Критический (Critical)
*   **Предусловия:** Открыта страница `/login`.
*   **Шаги:**
    1. В поле "Email/Логин" ввести пейлоад: `' OR '1'='1' --`.
    2. В поле "Пароль" ввести произвольный текст: `password123`.
    3. Нажать кнопку «Войти» (или отправить POST-запрос через Burp Suite).
*   **Ожидаемый результат:**
    *   Сервер возвращает HTTP 401 Unauthorized.
    *   UI показывает стандартное сообщение: "Неверный логин или пароль" (без уточнения, существует ли пользователь в БД, чтобы избежать User Enumeration).
    *   В логах сервера отсутствует трассировка ошибки базы данных (Stack Trace).

#### Тест-кейс SEC-02: Инвалидация токена сессии (JWT) после выхода (Logout)
*   **Приоритет:** Высокий (High)
*   **Предусловия:** Пользователь авторизован, в инструментах разработчика (DevTools) скопирован актуальный `Access Token` (JWT).
*   **Шаги:**
    1. Нажать кнопку «Выйти из аккаунта» в интерфейсе.
    2. Перехватить запрос к защищенному эндпоинту `GET /api/v1/user/profile`, добавив в заголовок `Authorization: Bearer <скопированный_токен>`.
    3. Отправить запрос через Postman.
*   **Ожидаемый результат:**
    *   Сервер возвращает HTTP 401 Unauthorized.
    *   Токен добавлен в "Blacklist" на сервере (или время его жизни истекло принудительно), доступ к данным профиля закрыт.

#### Тест-кейс SEC-03: Хранимый XSS (Cross-Site Scripting) в комментариях к товару
*   **Приоритет:** Высокий (High)
*   **Предусловия:** Авторизованный пользователь находится на странице товара.
*   **Шаги:**
    1. В поле "Оставить отзыв" ввести пейлоад: `<script>alert(document.cookie)</script>`.
    2. Нажать «Опубликовать».
    3. Обновить страницу товара.
    4. Открыть страницу этого же товара под другим пользователем (или в режиме Инкогнито).
*   **Ожидаемый результат:**
    *   Скрипт не выполняется. Всплывающее окно (alert) не появляется.
    *   Текст отзыва отображается как безопасный HTML-текст (пейлоад экранирован): `&lt;script&gt;alert...&lt;/script&gt;`.

### 3. Нагрузочное тестирование (Performance / Load Testing)
**Объект:** API эндпоинт поиска товаров `/api/v1/search?q={query}`.

#### Тест-кейс PERF-01: Стресс-тестирование (Stress Testing) - Поиск точки отказа
*   **Приоритет:** Высокий (High)
*   **Предусловия:** Тестовый стенд развернут, БД заполнена 10 млн товаров. Инструмент: JMeter / k6.
*   **Шаги:**
    1. Настроить сценарий с линейным ростом нагрузки: от 100 до 10 000 RPS (запросов в секунду) в течение 15 минут.
    2. Запустить тест.
    3. Проанализировать графики времени отклика (Response Time) и количества ошибок (Error Rate).
*   **Ожидаемый результат:**
    *   До 3000 RPS 95-й перцентиль (p95) времени отклика составляет < 200 мс.
    *   При достижении 5000 RPS сервер не падает с HTTP 500 / OOM (Out of Memory), а начинает корректно отдавать HTTP 429 (Too Many Requests), защищая базу данных от перегрузки (срабатывает Rate Limiter).

#### Тест-кейс PERF-02: Тестирование стабильности (Soak / Endurance Testing)
*   **Приоритет:** Средний (Medium)
*   **Предусловия:** Настроена стабильная нагрузка 80% от пиковой (например, 2500 RPS).
*   **Шаги:**
    1. Запустить подачу постоянной нагрузки на эндпоинт поиска на 24 часа.
    2. Мониторить потребление RAM и CPU на серверах приложений (App Servers) и БД.
*   **Ожидаемый результат:**
    *   Утечки памяти (Memory Leaks) отсутствуют (график потребления RAM стабилен, GC - Garbage Collection работает корректно).
    *   Время отклика к концу 24-часового теста не деградирует и остается на уровне p95 < 250 мс. Соединения с БД (Connection Pool) не исчерпываются.

#### Тест-кейс PERF-03: Spike Testing (Резкий скачок трафика)
*   **Приоритет:** Средний (Medium)
*   **Предусловия:** Эмулируется старт распродажи ("Черная пятница").
*   **Шаги:**
    1. Поддерживать фоновую нагрузку 200 RPS в течение 5 минут.
    2. Мгновенно (за 10 секунд) увеличить нагрузку до 8000 RPS.
    3. Удерживать 5 минут, затем резко сбросить до 200 RPS.
*   **Ожидаемый результат:**
    *   Во время скачка система может временно увеличить время отклика (до 1-2 секунд), но не должна терять коннект с БД.
    *   После снижения нагрузки система должна автоматически масштабироваться вниз (если используется Auto-scaling) и время отклика должно вернуться к базовым значениям (<150 мс) в течение 2 минут.

### 4. Тестирование UI/UX и Доступности (Accessibility / a11y)
**Объект:** Форма регистрации нового пользователя на мобильном устройстве.

#### Тест-кейс UI-01: Адаптивность и поведение клавиатуры (Viewport & Keyboard)
*   **Приоритет:** Высокий (High)
*   **Предусловия:** Тестирование на реальном устройстве iPhone 13 (или эмулятор 390x844).
*   **Шаги:**
    1. Открыть страницу `/register`.
    2. Тапнуть по полю "Email".
    3. Обратить внимание на тип вызванной экранной клавиатуры и поведение скролла.
    4. Тапнуть по полю "Дата рождения".
*   **Ожидаемый результат:**
    *   При фокусе на "Email" вызывается клавиатура с символом `@` и `.com`. Страница автоматически скроллится так, чтобы поле ввода и кнопка "Зарегистрироваться" не перекрывались клавиатурой.
    *   При фокусе на "Дата рождения" вызывается нативный "барабан" (Date Picker) ОС, а не стандартная QWERTY-клавиатура.

#### Тест-кейс UI-02: Доступность (Accessibility) - Навигация с клавиатуры (Tab Index)
*   **Приоритет:** Средний (Medium)
*   **Предусловия:** Тестирование на десктопе (Chrome), мышь отложена в сторону.
*   **Шаги:**
    1. Установить фокус на адресную строку и нажать `Tab` для перехода к телу страницы.
    2. Последовательно нажимать `Tab` для перемещения по полям формы (Имя -> Email -> Пароль -> Чекбокс согласия -> Кнопка Submit).
    3. Находясь на Чекбоксе согласия, нажать `Space` (Пробел).
*   **Ожидаемый результат:**
    *   Фокус (Outline ring) четко виден на каждом элементе, порядок табов логичен (слева направо, сверху вниз), фокус не "застревает" и не пропадает.
    *   Нажатие `Space` на чекбоксе корректно ставит/снимает галочку (не требует обязательного клика мышью).

#### Тест-кейс UI-03: Валидация и ARIA-атрибуты для скринридеров
*   **Приоритет:** Средний (Medium)
*   **Предусловия:** Включен скринридер (NVDA для Windows или VoiceOver для macOS).
*   **Шаги:**
    1. Оставить поле "Пароль" пустым и нажать кнопку "Зарегистрироваться".
    2. Прослушать озвучку ошибки скринридером.
    3. Инспектировать DOM-дерево элемента с ошибкой.
*   **Ожидаемый результат:**
    *   Скринридер не просто читает красный текст "Обязательное поле", а связывает его с инпутом благодаря атрибутам.
    *   В коде поле ввода должно иметь атрибут `aria-invalid="true"` и `aria-describedby="error-password"`. Скринридер озвучивает: *"Поле Пароль, ошибка: Обязательное поле"*. Цветовое выделение (красный) дублируется иконкой (например, восклицательный знак) для дальтоников.
