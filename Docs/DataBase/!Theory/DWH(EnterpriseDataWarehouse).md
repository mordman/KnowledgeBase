# 📊 DWH: Корпоративное хранилище данных — полный гайд

## 🎯 Что такое DWH

**DWH (Data Warehouse, корпоративное хранилище данных)** — это централизованная аналитическая система, которая объединяет информацию из разных источников компании (CRM, ERP, 1С, веб-сайтов, мобильных приложений, файлов, API) в единое целое для построения отчётов, дашбордов и принятия стратегических решений.

**Ключевые свойства DWH:**
- 📚 **Предметная ориентация** — данные структурированы по бизнес-сущностям (клиенты, продажи, продукты)
- 🔄 **Интегрированность** — единые справочники, форматы и единицы измерения
- 📅 **Привязка ко времени** — хранение истории изменений за годы
- 🔒 **Неизменяемость** — загруженные данные не удаляются и не меняются «задним числом»

---

## 🆚 Главное отличие: OLTP vs OLAP

| Критерий | OLTP (операционные БД) | OLAP (DWH) |
|----------|------------------------|------------|
| **Цель** | Быстрая обработка транзакций | Аналитика и отчёты |
| **Типичные операции** | `INSERT`, `UPDATE`, `DELETE` | `SELECT` со сложными агрегациями |
| **Объём данных** | Текущие данные (месяцы) | Исторические данные (годы) |
| **Структура** | Нормализованная (3NF) | Денормализованная («звезда», «снежинка») |
| **Нагрузка** | Много коротких запросов | Мало, но тяжёлых запросов |
| **Пользователи** | Приложения, операторы | Аналитики, руководители, BI-системы |
| **Производительность** | Миллисекунды на транзакцию | Секунды–минуты на отчёт |

> 💡 **Простыми словами:** OLTP — это «кассовый аппарат», DWH — это «архив и аналитический отдел».

---

## ❓ Зачем бизнесу DWH?

**Проблемы, которые решает хранилище:**

- 🕵️ **Разрозненность данных** — информация разбросана по десяткам систем, нет единой картины
- 📉 **Несогласованность метрик** — маркетинг считает выручку по-своему, финансы — по-своему
- 🐢 **Нагрузка на операционные БД** — тяжёлые отчёты «тормозят» работу приложений
- 📊 **Отсутствие истории** — невозможно сравнить показатели год к году
- 🧩 **Сложность отчётности** — аналитик тратит 80% времени на сбор данных и только 20% — на анализ
- 🎯 **Медленные решения** — решения принимаются «на глаз», а не на основе данных

**Что даёт DWH:**
- ✅ **Единая версия правды** — все смотрят на одни и те же цифры
- ✅ **Быстрая аналитика** — дашборды обновляются в реальном времени
- ✅ **Исторический анализ** — тренды за 5–10 лет
- ✅ **ML и AI** — готовая база для моделей прогнозирования

## 🏗 Архитектура DWH: слои данных

Типичное хранилище состоит из нескольких уровней:

### 1. **Staging Area (сырая зона)**
- Хранение «как есть» из источника
- Минимальные преобразования
- Быстрая загрузка без потери данных

### 2. **ODS (Operational Data Store)**
- Оперативный слой для актуальных данных
- Используется для near real-time отчётности
- Переходное звено между OLTP и DWH

### 3. **Core DWH (ядро хранилища)**
- Очищенные, интегрированные данные
- Единая модель (обычно Data Vault или 3NF)
- Историчность и неизменяемость

### 4. **Data Marts (витрины данных)**
- Тематические подмножества для конкретных отделов
- Оптимизированы под BI-запросы
- Схемы «звезда» / «снежинка»

## 🔄 Как данные попадают в хранилище: ETL vs ELT vs ETLT

### 🟦 Классический ETL (Extract → Transform → Load)
```
Источники → Извлечение → Трансформация → Загрузка в DWH
```
**Когда использовать:** классические on-premise хранилища, Oracle, MS SQL Server

### 🟩 Современный ELT (Extract → Load → Transform)
```
Источники → Извлечение → Загрузка сырых → Трансформация внутри DWH
```
**Когда использовать:** облачные решения (Snowflake, BigQuery, ClickHouse Cloud) с мощными вычислительными ресурсами

### 🟨 ETLT (гибрид)
- Лёгкая первичная трансформация на этапе E
- Глубокая обработка внутри DWH

**Основные инструменты оркестрации:** Apache Airflow, Dagster, Prefect, Mage, dbt

## 📐 Подходы к проектированию

### 1. **Билл Инмон (Top-down) — «Хранилище как корпоративный стандарт»**
```
Источники → Единое корпоративное хранилище (3NF) → Витрины данных
```
- ✅ Строгая нормализация
- ✅ Единая версия правды
- ❌ Долгий старт проекта
- ❌ Сложная поддержка

### 2. **Ральф Кимбалл (Bottom-up) — «Быстрые победы через витрины»**
```
Источники → Витрины данных («звезда») → Виртуальное хранилище
```
- ✅ Быстрый запуск (первые результаты за месяцы)
- ✅ Понятные бизнес-схемы
- ❌ Риск несогласованных метрик
- ❌ Сложно консолидировать витрины

### 3. **Data Vault — «Гибкость для сложных систем»**
Состоит из трёх типов таблиц:
- 🔵 **Hub** — бизнес-ключи (ID клиента, ID заказа)
- 🔗 **Link** — связи между сущностями
- 🛰 **Satellite** — атрибутика и история изменений

- ✅ Идеально для частых изменений источников
- ✅ Отличная аудируемость
- ❌ Требует зрелой команды и много памяти

### 4. **Anchor Vault** — эволюция Data Vault
Более производительная альтернатива с использованием колоночных СУБД.

### 5. **One Big Table (OBT)** — современный подход
- Одна широкая таблица для BI
- Используется в связке с мощными колоночными БД
- Упрощает запросы для аналитиков

## 🛠 Технологический стек DWH

### 💾 СУБД и хранилища
| Категория | Примеры |
|-----------|---------|
| **Колоночные OLAP** | ClickHouse, DuckDB, Vertica |
| **MPP-платформы** | Greenplum, YTsaurus, Teradata |
| **Облачные DWH** | Snowflake, BigQuery, Redshift, Yandex Managed ClickHouse |
| **Open-source** | Apache Doris, StarRocks, Apache Pinot |

### ⚙️ Обработка данных
- **Пакетная обработка:** Apache Spark, Apache Beam, Apache Flink (batch mode)
- **Потоковая обработка:** Apache Kafka, Apache Flink, Apache NiFi
- **Оркестрация:** Apache Airflow, Dagster, Prefect
- **Трансформация:** dbt, Apache Spark SQL, Python-пайплайны

### 📊 BI и визуализация
- **Российские:** Yandex DataLens, PIX BI, Visiology, Modus BI
- **Международные:** Tableau, Power BI, Looker, Metabase, Apache Superset
- **Open-source:** Grafana, Apache Superset, Redash

### 🗂 Управление данными
- **Каталоги данных:** Apache Atlas, DataHub, Amundsen
- **Качество данных:** Great Expectations, Soda, Deequ
- **Линейность данных:** Marquez, OpenLineage

## 🌊 DWH vs Data Lake vs Lakehouse

| Параметр | DWH | Data Lake | Lakehouse |
|----------|-----|-----------|-----------|
| **Тип данных** | Структурированные | Любые (структура/неструктура) | Любые |
| **Схема** | Schema-on-Write | Schema-on-Read | Оба варианта |
| **Стоимость хранения** | Высокая | Низкая | Средняя |
| **Поддержка ACID** | Да | Обычно нет | Да (Delta Lake, Iceberg) |
| **Применение** | BI, отчётность | ML, Data Science | Универсально |
| **Примеры** | Snowflake, Greenplum | AWS S3, HDFS, Yandex Object Storage | Databricks, YTsaurus |

> 💎 **Lakehouse** — современный гибрид, объединяющий лучшие черты DWH и Data Lake.

## 👥 Роли в команде DWH

- 🏗 **Data Architect** — проектирует архитектуру и модели данных
- 🔧 **Data Engineer** — строит ETL-пайплайны и инфраструктуру
- 🧮 **Analytics Engineer** — создаёт витрины и метрики (обычно работает в dbt)
- 📈 **BI-аналитик** — строит дашборды и отчёты
- 🔬 **Data Scientist** — использует данные для ML-моделей
- 🕵️ **Data Steward** — отвечает за качество и глоссарий данных

---

## 🚀 Современные тренды

- 🌐 **Data Mesh** — децентрализация: каждая бизнес-домен отвечает за свои данные как за «продукт»
- 📦 **Data Products** — данные как продукт с SLA, документацией и владельцем
- 🧬 **Data Contracts** — формальные соглашения между источником и потребителем данных
- ⚡ **Real-time DWH** — потоковая аналитика в реальном времени
- 🤖 **AI-ассистенты** — Text-to-SQL и автоматическая генерация дашбордов
- 🏢 **Embedded Analytics** — аналитика, встроенная прямо в бизнес-приложения

---

## 📈 Когда компании нужен DWH?

**Вам стоит задуматься о DWH, если:**
- ✅ В компании более 5 источников данных
- ✅ Аналитики тратят больше времени на сбор данных, чем на анализ
- ✅ Метрики в разных отчётах не совпадают
- ✅ Нужна история изменений за 3+ года
- ✅ Отчёты формируются дольше 10 минут
- ✅ Есть потребность в прогнозировании и ML
- ✅ Компания растёт и готовится к масштабированию
